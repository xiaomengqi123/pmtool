# PMTool 自动部署与回滚

仓库中的 [GitHub Actions 工作流](../.github/workflows/deploy.yml) 会在 `main` 分支推送后构建前后端并发布到 Ubuntu。首次安装仍须按 [上线检查清单](上线检查清单.md) 完成 Java、MySQL、MinIO、Nginx、systemd 和 `/etc/pmtool/pmtool.env` 配置。

## GitHub 仓库配置

在仓库 **Settings → Environments → production** 创建环境，并配置以下 Actions Secrets：

| 名称 | 说明 |
| --- | --- |
| `PMTOOL_SSH_HOST` | 服务器 IP 或主机名。 |
| `PMTOOL_SSH_PORT` | SSH 端口，通常为 `22`。 |
| `PMTOOL_SSH_USER` | 有权限写入 `/opt/pmtool`、重启 `pmtool` 服务的部署用户。建议使用专用部署账号，不使用日常登录账号。 |
| `PMTOOL_SSH_PRIVATE_KEY` | 部署用户对应的私钥；公钥写入服务器 `authorized_keys`。 |
| `PMTOOL_SSH_FINGERPRINT` | 服务器 SSH 主机密钥 SHA256 指纹，用于防止连接到错误主机。 |

服务器的 `/etc/pmtool/pmtool.env` 仅保存在服务器，不能放入 GitHub Secrets 再由工作流覆盖。它包含数据库、JWT、初始管理员和对象存储凭据。

## 发布机制

1. 工作流运行后端测试和 JAR 构建，以及前端生产构建。
2. 使用与人工发布相同的 `package-release.sh` 将 JAR、前端静态文件和运维脚本打包并上传服务器临时目录。
3. `release.sh` 解包到 `/opt/pmtool/releases/<commit-sha>`，通过原子替换 `/opt/pmtool/current` 软链接切换版本，再重启服务并执行健康检查。
4. 失败时，脚本自动将 `current` 恢复到 `previous`，重新启动服务；保留最近五个版本。

数据库 Flyway 迁移只向前执行。应用文件可自动恢复，但数据库模式或数据不能自动回滚；含破坏性迁移的版本必须先进行备份和人工评审。

## 手动回滚

在服务器执行：

```sh
sudo /opt/pmtool/deploy/rollback.sh
```

随后运行：

```sh
sudo /opt/pmtool/deploy/verify-deployment.sh
```

也可以从 Actions 的 **Run workflow** 手动选择 `rollback`。回滚前先确认目标版本与当前数据库 Flyway 版本兼容。
